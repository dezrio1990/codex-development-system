# Codex Development System Lite

Статус: предложено к утверждению  
Дата: 2026-09-14  
Язык документации: русский; английские термины сопровождаются русским пояснением.

## 1. Назначение

Репозиторий хранит утверждённые правила разработки, профили субагентов и шаблоны проектной документации. Он не является программным продуктом, установщиком или системой управления конфигурацией.

Главный критерий — правила легко читать, обсуждать, версионировать и вручную подключать к проектам через Codex.

## 2. Упрощённая структура

```text
codex-development-system/
├── AGENTS.md
├── README.md
├── CHANGELOG.md
├── current/
│   ├── rules/
│   ├── roles/
│   └── templates/
├── versions/
│   └── 1.0/
│       ├── rules/
│       ├── roles/
│       ├── templates/
│       └── VERSION.md
└── examples/
    └── codex-rules.json
```

- `current/` — следующая редактируемая редакция.
- `versions/<номер>/` — неизменяемый снимок утверждённых документов.
- `AGENTS.md` — короткие глобальные инструкции: порядок согласований, выбор ролей и ссылка на актуальные документы.
- `CHANGELOG.md` — понятное человеку описание различий между версиями.
- `examples/codex-rules.json` — пример привязки проекта к версии.

## 3. Подключение проекта

В проект добавляется небольшой файл `.codex/codex-rules.json`:

```json
{
  "source": "https://github.com/dezrio1990/codex-development-system",
  "version": "1.0",
  "profiles": ["base", "dotnet"]
}
```

При создании проекта Codex читает этот файл и вручную копирует необходимые утверждённые документы из `versions/<version>/` в `.codex/rules/`. Никакой установочный скрипт не требуется.

Локальная копия правил позволяет новому контексту Codex и субагентам работать без зависимости от сети. Источником версии остаётся центральный Git-репозиторий.

## 4. Выпуск новой версии

1. Изменения готовятся в `current/`.
2. Пользователь просматривает и утверждает содержательные изменения.
3. Codex копирует `current/` в новую папку `versions/<номер>/`.
4. Обновляются `CHANGELOG.md` и `VERSION.md`.
5. Выпуск сохраняется одним логическим Git-коммитом и тегом.

После выпуска содержимое папки версии не редактируется. Исправления выпускаются новой версией.

Git обеспечивает историю, сравнение и восстановление. Дополнительные checksums, release hashes и собственные валидаторы не используются.

## 5. Обновление существующего проекта

Проект может бессрочно оставаться на старой версии.

Обновление выполняется только по явному запросу пользователя:

1. Codex сравнивает старую и новую папки версий через Git diff.
2. Кратко сообщает изменения правил и возможное влияние на проект.
3. Согласовывает переход с пользователем.
4. Обновляет локальную копию `.codex/rules/` и поле `version`.
5. Проверяет, что документы читаются и ссылки на файлы существуют.

Автоматические миграции, транзакции, rollback-движок и хеширование не применяются. При необходимости откат выполняется обычным Git revert либо возвратом номера версии после согласования.

## 6. Рабочий процесс Codex и субагентов

- Архитектура, стек и план согласовываются перед каждым существенным этапом.
- Для одного содержательного изменения используется один исполнитель.
- Субагенты подключаются только когда специализация или параллельность действительно улучшает результат.
- Code review обязателен для программного кода приложения, но не для каждой правки Markdown.
- Документация проверяется одним содержательным просмотром: ясность, непротиворечивость, отсутствие незаполненных `TODO/TBD`, корректность локальных ссылок.
- Программные тесты запускаются для приложений и исполняемых инструментов, но не для обычного набора правил.
- Один согласованный этап оформляется одним логическим коммитом; промежуточные исправления не требуют отдельной версии продукта.

## 7. Что удаляется из предыдущей архитектуры

- PowerShell installer, initializer, validator, synchronizer и publisher.
- Тестовые harness и наборы тестов этих скриптов.
- JSON Schema для внутренних manifest-файлов.
- Checksums и собственные content hashes.
- Автоматическая проверка двух редакций PowerShell.
- Транзакционный filesystem rollback и отчёты автоматической миграции.
- CI для тестирования самих документов.

Содержательные правила, роли, шаблоны, утверждённые ограничения и русскоязычная документация сохраняются.

## 8. Проверка готовности версии

Перед выпуском достаточно одного короткого checklist:

- все обязательные документы присутствуют;
- номер версии совпадает с именем папки и `VERSION.md`;
- нет `TODO`, `TBD` и противоречащих правил;
- локальные ссылки существуют;
- `CHANGELOG.md` объясняет изменения;
- пользователь утвердил выпуск;
- Git working tree не содержит случайных файлов.

## 9. Переход с текущей реализации

После утверждения этой спецификации выполняется один cleanup-этап:

1. Сохранить полезные правила, роли и шаблоны.
2. Привести их к структуре Lite.
3. Удалить исполняемую инфраструктуру и её тесты.
4. Создать компактный `README.md`, `CHANGELOG.md`, `VERSION.md` и пример привязки.
5. Провести один содержательный просмотр и показать итог пользователю.
6. До первой публикации сформировать чистую понятную историю репозитория отдельным согласованным действием.

Удалённый GitHub-репозиторий, push и перенос в `D:\Projects\codex-development-system` остаются отдельным этапом и требуют явного подтверждения пользователя.

## 10. Критерий успеха

Новый проект можно подключить к выбранной версии правил, прочитав один JSON-файл и скопировав соответствующие документы. Поддержка системы не требует запуска PowerShell или изучения внутреннего механизма миграций.
