# Codex Development System

Центральный репозиторий правил для разработки приложений вместе с Codex и специализированными субагентами. Он помогает сохранять единый процесс, качество и управляемость проектов без установщиков и сложной автоматизации.

## Как устроен репозиторий

- `current/` — рабочая редакция будущей версии.
- `versions/<номер>/` — утверждённые неизменяемые версии.
- `rules/` — общие правила разработки и согласований.
- `roles/` — обязанности специализированных субагентов.
- `templates/` — шаблоны проектной документации и технологические профили.
- `examples/codex-rules.json` — пример привязки проекта к версии.

Версия `1.0` может использоваться сколько угодно долго. Новая версия правил не переводит существующие проекты автоматически.

## Доступные профили

- `base` — общие правила и базовые проектные документы;
- `dotnet` — серверные и веб-приложения на .NET;
- `web` — веб-интерфейсы;
- `android` — нативные приложения Kotlin и Jetpack Compose;
- `ios` — нативные приложения Swift и SwiftUI;
- `dotnet-maui` — общие мобильные приложения C# и .NET MAUI.

Профиль `base` используется всегда. Остальные выбираются по фактическому стеку проекта.

## Подключение к новому проекту

### 1. Создайте файл привязки

Добавьте в новый проект `.codex/codex-rules.json`:

```json
{
  "source": "https://github.com/dezrio1990/codex-development-system",
  "version": "1.0",
  "profiles": [
    "base",
    "dotnet"
  ]
}
```

Замените `dotnet` нужным профилем или перечислите несколько профилей.

### 2. Попросите Codex подключить правила

Используйте запрос:

```text
Подключи к этому проекту Codex Development System версии 1.0 с профилями
base и dotnet. Прочитай .codex/codex-rules.json, возьми документы из
versions/1.0 центрального репозитория и скопируй применимые правила в
.codex/rules этого проекта. Не начинай разработку до моего подтверждения.
```

Codex копирует в проект общие правила, выбранные профили и необходимые шаблоны. Локальная копия нужна, чтобы новый контекст и субагенты могли работать без сети.

Точная карта подключения:

| Источник в `versions/<version>/` | Назначение в проекте | Правило |
|---|---|---|
| `rules/base.md` | `.codex/rules/base.md` | Копируется всегда. |
| `roles/*.md` | `.codex/rules/roles/*.md` | Копируются все роли, чтобы они были доступны новому контексту. |
| `templates/base/**` | корень проекта | Подставляются значения шаблонов; существующие файлы не перезаписываются без согласования. |
| `templates/overlays/<profile>/AGENTS.append.md` | `.codex/rules/profiles/<profile>/AGENTS.md` | Копируется для каждого выбранного профиля. |
| `templates/overlays/<profile>/overlay.json` | `.codex/rules/profiles/<profile>/profile.json` | Сохраняет инструменты и команды проверки профиля. |
| `templates/overlays/<profile>/AGENTS.append.md` | конец корневого `AGENTS.md` | Добавляется один раз после базовых правил проекта. |

Если целевой файл уже существует, Codex сначала показывает различия и предлагает способ объединения. Без вашего подтверждения существующий файл не изменяется.

### 3. Начните проект с согласования

Готовый запрос для нового проекта:

```text
Создай новый проект <название>. Используй Codex Development System версии 1.0
и профили base, <профиль>. Сначала прочитай закреплённые правила, затем предложи
архитектуру, стек и этапы. Не начинай существенную реализацию до моего утверждения.
```

После подключения основной Codex читает локальные правила и передаёт применимые ограничения каждому субагенту. Субагент также должен прочитать свою роль и активную проектную документацию до начала работы.

## Рекомендуемые файлы внутри проекта

```text
<project>/
├── AGENTS.md
├── .codex/
│   ├── codex-rules.json
│   └── rules/
│       ├── base.md
│       ├── README.md
│       ├── roles/
│       └── profiles/
└── docs/
    ├── architecture/
    ├── product/
    ├── requirements/
    ├── plans/
    ├── quality/
    └── status/
```

В `AGENTS.md` проекта достаточно указать закреплённую версию и потребовать чтения `.codex/rules/` перед работой.

## Обновление проекта на новую версию

Обновление выполняется только по вашему запросу:

```text
Сравни правила, закреплённые в этом проекте, с Codex Development System версии
1.1. Покажи изменения, влияние на архитектуру, документацию и код. Ничего не
изменяй до моего утверждения плана перехода.
```

После утверждения Codex обновляет `.codex/rules/` и поле `version` в `.codex/codex-rules.json`. Если обновление не требуется, проект продолжает работать на старой версии.

Для возврата используется Git revert либо согласованная установка прежнего номера версии и соответствующей копии правил.

## Выпуск новой версии правил

1. Измените документы в `current/`.
2. Просмотрите различия и согласуйте их с пользователем.
3. Скопируйте `current/` в новую папку `versions/<номер>/`.
4. Создайте `VERSION.md` и обновите `CHANGELOG.md`.
5. Сохраните выпуск одним логическим коммитом и Git-тегом.

Опубликованная папка версии не редактируется. Исправление оформляется новой версией.

## Проверка документации

PowerShell и программные тесты не требуются. Перед выпуском достаточно убедиться, что обязательные документы присутствуют, локальные ссылки существуют, `CHANGELOG.md` заполнен, а в текстах нет незавершённых решений или противоречий.

Историю, сравнение и восстановление обеспечивает Git.
